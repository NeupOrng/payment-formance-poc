# CLAUDE.md

POC for using **Formance Ledger** as the core ledger of a mobile bank's payment system, with payment orders run as **Temporal sagas**. The schema follows the planned *Payment Engine & Profile Schema*. [docs/05-schema.md](docs/05-schema.md) describes the implemented model.

## Repository layout

| Path | Purpose |
| --- | --- |
| `profile/` | NestJS + Drizzle. Profile Service: `profile` (individual / agent / internal), `account_product`, `stock` (one per currency). Mirrors stock balances from Formance ledger events. Port 4001 |
| `payment/` | NestJS + Drizzle + Temporal. Payment Engine: service configuration (groups, services, commands, tiers with amount rules and balance movements, SPIs) and payment orders run by the `orderSaga` workflow; the only code that writes to Formance. Port 4002 |
| `partner-mock/` | Mock biller used as an external SPI (validations, confirmations, failure switch). Port 4003 |
| `client/` | Nuxt 4 + shadcn-vue + Tailwind v4 console: profiles, stocks, payment orders, service configuration (see `client/CLAUDE.md`). Port 4000 |
| `architecture/` | Docker Compose dev environment (Postgres, Formance, Temporal, services), Postgres init, `scripts/smoke.mjs` |
| `bruno/` | Bruno API collection: every endpoint with tests (`task bruno`) |
| `docs/` | Proposal, architecture, schema, plan |
| `Taskfile.yml` | All dev commands |

## Commands

```bash
task dev        # up + seed + smoke test + Bruno collection (the full check)
task up / down / reset / logs -- payment-service
task seed       # bank profile, agent, amount types, SPIs, example services and tiers
task test       # vitest in profile and payment
task typecheck  # profile, payment and client
task smoke      # end-to-end checks against the running stack (needs the seed)
task bruno      # Bruno collection (self-contained)
task db:generate -- payment   # after editing src/db/schema.ts
```

- **UIs:** Temporal at http://localhost:8233 (every order's saga history), the console at http://localhost:4000, and Swagger at `:4001/docs` and `:4002/docs`.
- **Hot reload:** the stack reloads on save. After changing a `package.json`, run `task rebuild`.

## Secrets

- **Never commit credentials.** Local database passwords live in `architecture/.env`, which is gitignored and generated by `task env` from `architecture/.env.example`.
- `docker-compose.yml` reads them with `${VAR:?}`, and `postgres/init.sh` creates the service roles from them.
- `drizzle.config.ts` reads `DATABASE_URL` from the environment and has no default.
- **SPI credentials:** `spi_external_config.credential_ref` stores the *name* of a secret (an env var locally, a vault key in production), never the secret.
- When adding a secret, add an empty key to `.env.example`. `task env` only fills a new key when it creates the file, so if `.env` already exists, add the key to it by hand.

## Stack conventions

- **NestJS 12 is ESM-only.** Relative imports need the `.js` extension.
- **Drizzle ORM 0.45 with `node-postgres`.** Schema in `src/db/schema.ts`; migrations in `drizzle/`, applied on start-up. Never edit an applied migration; add a new one. Use `drizzle-kit generate --custom` for SQL Drizzle can't express (e.g. the `EXCLUDE` constraint in `payment/drizzle/0001_*`). If drizzle-kit would ask "renamed or new?", split the change into two generates.
- **Enums are Postgres enums** (`pgEnum`), as in the planned schema. Their values are exported and reused in DTOs.
- **Each service has its own database and role.** Cross-service references (customer, stock ids) are plain UUIDs.
- **Services talk over HTTP:** the payment engine calls the Profile Service through `ProfileClient`.
- **Validation:** a global `ValidationPipe` with `whitelist` and `forbidNonWhitelisted`. A route `@Param()` DTO must declare **every** route param.
- **Temporal:**
  - **Workflows** (`payment/src/temporal/workflows.ts`) run in a deterministic sandbox: only `@temporalio/workflow` and **type-only** imports, no I/O. Every side effect is an activity.
  - **Activities** must be idempotent; Temporal retries them.
  - **Payloads** are JSON, so amounts travel as decimal strings.
  - **Worker image:** the worker runs inside the payment service (`RUN_WORKER=false` disables it) and needs a glibc image (`node:24-bookworm-slim`).
- **Tests:** vitest (`*.spec.ts`). Keep money logic pure and unit-tested:
  - `pricing/expression.ts` and `pricing/pricing.ts`: rules and formulas.
  - `movement/movement.ts`: movements and the ledger plan.

## Domain rules (do not break these)

- **Formance is the only source of truth for money.**
  - The Profile Service's `stock.ledger_balance` / `hold_amount` / `available_balance` are a read model, recomputed from Formance on each ledger event. Never authorize spending from them, and never write them from anywhere else.
  - Funds checks happen in Formance.
- **Only the payment engine writes to Formance.** The Profile Service only reads it, to mirror balances.
- **Money:**
  - Amounts are `NUMERIC(20,2)` in Postgres and decimal strings in APIs.
  - The code computes in `bigint` minor units (`common/money.ts`) or exact fractions (`pricing/expression.ts`). Never use JS `number` for money.
  - Formance assets are `USD/2` and `KHR/2`.
- **One currency per service.** Payer, payee and every `SPECIFIC` stock must be in the service's currency.
- **An order request carries only** service code, amount, payer stock, payee stock (and an optional external reference).
  - Every other amount comes from the matched tier's `tier_amount_rule`s.
  - Who pays and receives comes from its `balance_movement_config`.
  - To change prices or money flows, change configuration (a new tier), not code.
- **Tiers are immutable** once created, because orders reference them. Deactivate a tier and create a new one. Active tier ranges `[min, max)` of a command must not overlap.
- **Every order is a saga** (`orderSaga`): prepare → RESERVE → (authorization) → PRE_PAYMENT SPIs → SETTLE → POST_PAYMENT SPIs → COMPLETED → NOTIFICATION.
  - Compensation is new ledger transactions (REVERT, RELEASE), never edits.
  - Ledger references are `{orderId}:{step}`, so a step posts once.
- **Every order-creating endpoint requires an `Idempotency-Key`** (≤ 64 characters), unique per payer profile. It also determines the workflow id.
- **Only `INTERNAL` (bank) stocks may go negative.** Customer and agent stocks never can.
- **No personal data in ledger addresses or metadata,** only ids.
- **Status reason codes fit `VARCHAR(20)`.**
- **Cards are out of scope for now.**
